# 数据库设计规范

## 1. 设计原则

### 1.1 规范化与反规范化平衡
- 在满足第三范式的基础上，适当反规范化以提高查询性能
- 权衡数据一致性与查询效率

### 1.2 性能考虑
- 设计时考虑查询性能
- 避免大数据量单表存储
- 合理使用分区表

### 1.3 扩展性
- 预留扩展字段（谨慎使用）
- 支持水平扩展的设计
- 版本管理考虑

## 2. 命名规范

### 2.1 表命名
- 使用小写字母和下划线
- 前缀统一（如：sys_系统表, gen_生成表, monitor_监控表）
- 见名知意，长度不超过30个字符
- 示例：`sys_user`, `sys_dept`, `gen_table`

### 2.2 字段命名
- 使用小写字母和下划线
- 避免使用保留字
- 通用字段名统一
  - 主键：`{业务}_id` (如：user_id, dept_id)
  - 创建时间：`create_time`
  - 更新时间：`update_time`
  - 创建人：`create_by`
  - 更新人：`update_by`
  - 删除标志：`del_flag`
  - 租户ID：`tenant_id`（如使用多租户）

### 2.3 索引命名
- 主键：`PK_{表名}`
- 唯一索引：`UK_{表名}_{字段名}`
- 普通索引：`IDX_{表名}_{字段名}`
- 组合索引：`IDX_{表名}_{字段1}_{字段2}`

## 3. 数据类型选择

### 3.1 数值类型
- 主键：BIGINT（使用雪花算法）
- 一般整数：INT
- 小数：DECIMAL(precision, scale)
- 位运算：BIT

### 3.2 字符类型
- 短字符串：VARCHAR(长度明确)
- 长文本：TEXT
- 固定长度：CHAR
- JSON：JSON类型（MySQL 5.7+）

### 3.3 时间类型
- 创建时间、更新时间：DATETIME
- 仅日期：DATE
- 仅时间：TIME
- 带时区的时间：TIMESTAMP

## 4. 表结构规范

### 4.1 通用字段
每个表都应该包含以下通用字段（除历史表、日志表等特殊情况）：

```sql
-- 通用字段示例
CREATE TABLE sys_user (
    user_id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    tenant_id VARCHAR(20) DEFAULT '' COMMENT '租户ID',
    user_name VARCHAR(30) NOT NULL COMMENT '用户账号',
    nick_name VARCHAR(30) NOT NULL COMMENT '用户昵称',
    email VARCHAR(50) DEFAULT '' COMMENT '用户邮箱',
    phone_number VARCHAR(11) DEFAULT '' COMMENT '手机号码',
    sex CHAR(1) DEFAULT '0' COMMENT '用户性别（0男 1女 2未知）',
    avatar VARCHAR(100) DEFAULT '' COMMENT '头像地址',
    password VARCHAR(100) DEFAULT '' COMMENT '密码',
    status CHAR(1) DEFAULT '0' COMMENT '帐号状态（0正常 1停用）',
    del_flag CHAR(1) DEFAULT '0' COMMENT '删除标志（0代表存在 2代表删除）',
    login_ip VARCHAR(128) DEFAULT '' COMMENT '最后登录IP',
    login_date DATETIME COMMENT '最后登录时间',
    create_by VARCHAR(64) DEFAULT '' COMMENT '创建者',
    create_time DATETIME NOT NULL COMMENT '创建时间',
    update_by VARCHAR(64) DEFAULT '' COMMENT '更新者',
    update_time DATETIME COMMENT '更新时间',
    remark VARCHAR(500) DEFAULT NULL COMMENT '备注',
    PRIMARY KEY (user_id)
) ENGINE=InnoDB COMMENT='用户信息表';
```

### 4.2 主键设计
- 使用BIGINT类型的自增主键
- 使用雪花算法生成分布式ID
- 避免使用UUID作为主键（性能问题）
- 不使用业务字段作为主键

### 4.3 软删除
- 使用`del_flag`字段实现软删除
- '0': 未删除, '2': 已删除
- 在查询时默认过滤已删除数据

## 5. 索引设计

### 5.1 索引策略
- 主键自动创建唯一索引
- 外键字段建立普通索引
- 经常查询的字段建立索引
- 避免过度索引影响写入性能

### 5.2 索引类型选择
- 等值查询：普通索引
- 唯一性约束：唯一索引
- 大文本模糊查询：全文索引
- 范围查询：普通索引

### 5.3 复合索引
- 遵循最左前缀原则
- 高选择性字段放前面
- 频繁使用的查询条件组合建立复合索引

## 6. 外键与约束

### 6.1 外键使用
- 一般情况下不使用物理外键
- 通过应用程序维护数据完整性
- 降低数据库层面的耦合度

### 6.2 约束设计
- 使用NOT NULL约束
- 使用CHECK约束验证数据有效性
- 使用UNIQUE约束保证数据唯一性

## 7. 分区与分表

### 7.1 分区策略
- 按时间分区（适用于日志、历史数据）
- 按业务维度分区
- 考虑查询和维护便利性

### 7.2 分表策略
- 按时间分表
- 按业务分表
- 使用分库分表中间件

## 8. 安全考虑

### 8.1 权限控制
- 按角色分配数据库权限
- 最小权限原则
- 敏感数据访问控制

### 8.2 敏感数据
- 密码等敏感信息加密存储
- 脱敏显示
- 审计日志记录

## 9. 多租户设计

### 9.1 租户隔离
- 使用tenant_id字段实现数据隔离
- 在查询中默认添加租户条件
- 租户间数据完全隔离

### 9.2 租户数据管理
- 租户配置信息独立存储
- 租户资源配额管理
- 租户数据迁移策略

## 10. 版本管理

### 10.1 数据库版本控制
- 使用Flyway或Liquibase管理
- 数据库变更脚本化
- 版本号与应用版本对应

### 10.2 变更管理
- 变更前备份数据
- 变更后验证数据完整性
- 回滚方案准备

## 11. 性能优化

### 11.1 查询优化
- 避免SELECT *
- 合理使用分页
- 优化JOIN操作
- 使用EXPLAIN分析查询计划

### 11.2 表设计优化
- 垂直拆分大表
- 水平拆分大表
- 合理设计字段类型

## 12. 监控与维护

### 12.1 监控指标
- 表大小监控
- 索引使用率
- 查询性能监控
- 锁等待监控

### 12.2 维护策略
- 定期分析表统计信息
- 索引重建或重组
- 数据归档策略
- 备份恢复策略

### 13.1 代码生成器兼容
- 设计时考虑代码生成器的支持
- 字段注释规范

### 13.2 系统表规范
- 系统管理相关表设计规范
